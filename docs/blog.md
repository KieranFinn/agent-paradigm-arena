# 当模型足够强，范式还剩下什么？

## ——ReAct / Plan-and-Execute / Reflexion 的 123 次真实运行对照实验

> 结论先行：**在 2026 年的中等强度模型上，三种 Agent 范式的成功率没有任何差别（105/105 全部通过，主场客场一视同仁）。范式之间的差异全部转移到了成本结构上：Plan-and-Execute 贵 3 倍、慢 3 倍、首次动手晚 10 秒；Reflexion 的"反思"外环在全部 18 次运行中一次都没有触发。**
>
> 本文的每个数字都可以回溯到实验仓库里某一条具体的事件序列（trace）。实验代码、任务设计、预注册假设全部开源：[KieranFinn/agent-paradigm-arena](https://github.com/KieranFinn/agent-paradigm-arena)。

**实验配置**：DeepSeek-V4.1-Flash（`deepseek-flash`，temperature=0）· 4 智能体 × 3 任务 × 2 难度 · 123 次正式运行 · 总花费 ¥7.01（含探针与废弃批次的全账本为 205 次运行、¥10.89）。

## 一、背景：为什么"范式优劣"的讨论大多不可信

网上关于 ReAct / Plan-and-Execute / Reflexion 的对比文章，大多过不了三道审计：

1. **没有 null baseline。** "ReAct 在 X 任务上成功率 80%"——那不用任何脚手架、单次调用直接做呢？如果单次调用也能 80%，脚手架加的 0 分会让人重新审视那 80% 是模型的还是范式的。
2. **没有成本账本。** 只报成功率，不报 token、不报钱、不报延迟。一个 95% 成功但每次烧 ¥1 的方案，和一个 90% 成功每次 ¥0.03 的方案，工程上是两个物种。
3. **没有可回溯的 trace。** 结论无法复核，失败无法复现，"ReAct 容易目标漂移"这种论断永远停留在引用论文的阶段。

这个实验仓库就是为了过这三道审计而建的：

- **CoT 基线行**：4×3 矩阵里有一行没有工具、只有一次调用的"裸模型"，回答"脚手架到底加了多少分"；
- **每个格子 N 次重复 + Wilson 95% 置信区间**：单次运行的波动不配成为结论；
- **统一工具层、统一评估器、统一 trace 格式**：三个范式共享除控制流以外的一切——改范式不可能无意中改到考场；
- **模拟服务时钟 + 三档计价**（cached input ¥0.2 / fresh input ¥2 / output ¥8 每百万 token）：网络抖动不进主表，成本可对账。

顺带交代几个**主动否决**的设计（它们决定了实验的有效性）：

| 被否决的做法 | 问题 |
|---|---|
| 按"各范式擅长的任务"选任务 | 同义反复，结论必然"各有主场" |
| 3×3 只跑对角线 | 缺对照组，无法回答"脚手架加了多少分" |
| 用代码行数比工程量 | 与范式优劣无关 |
| "token 随轮数二次方增长" | 那是 API 无状态的特性，不是 ReAct 的——必须拆成「峰值 prompt」（可归因范式）和「累计 token」（所有范式都要付的重发税）分别看 |

## 二、三种范式：控制流深描

三个范式的完整实现都是最小原型（141–287 行），共享同一套工具、任务和评估器。差异只在控制流。

### 2.1 ReAct：一条只增不减的消息列表

```text
messages = [system] + [task]
loop:
    msg = llm.chat(messages, tools)        # 每轮重发全量 messages
    messages.append(msg)
    无 tool_call 且以 FINAL: 开头 → 返回
    逐个执行 tool_calls，结果 JSON 回填为 role:"tool"
    同一 (tool, 归一化参数) 连续出现 ≥3 次 → 护栏事件 + 错误回填
    单条结果 >4000 字符 → 裁剪后入上下文
```

它的结构性特征（也是全部争议所在）：`messages` **永不收缩**。第 N 轮的 prompt 包含前 N−1 轮的全部工具结果。上下文膨胀是它最著名的"致命缺陷"——但请注意第一节的那条否决：膨胀的**峰值**（单次 prompt 多大）是范式特性，膨胀的**累计**（一共发了多少 token）是 API 无状态特性，任何多轮范式都要付。本文两个都量了。

它的隐性优势在一条真实 trace 里看得很清楚（探针批次 `react_T1_easy`）：

```text
[19.3s] apply_patch  {"old": "EXPECTED_INVOICE_HASH = 'a3f1c9e2b7d4'", ...}
[19.3s]   -> ok=false kind=arg  old snippet not found in 'hashes.py'
[24.6s] apply_patch  {"old": "EXPECTED_INVOICE_HASH = \"a3f1c9e2b7d4\"", ...}
[24.6s]   -> ok=true  replaced=1
```

第一次补丁用错了引号，工具返回 `kind=arg`（参数错误，模型可自愈），下一轮立刻修正。**错误分层是自愈的前提**：`arg` 类错误（参数错/锚点不存在）和 `tool` 类错误（环境限制，重试无用）回给模型的是不同的 JSON，模型据此选择"修正调用"还是"改变策略"。

### 2.2 Plan-and-Execute：Step 是显式对象

```text
Planner   → 严格 JSON 计划 {steps:[{id, goal, depends_on, hint}]}（≤8 步）
Execute   → 拓扑取就绪集 → 线程池并行执行
            每个 step 的上下文恒定 = 任务 + 上游结果 + 本步目标 + hint
失败      → Step 状态 PENDING→RUNNING→DONE/FAILED/SKIPPED
            FAILED 触发 Re-planner：local 只换失败节点及其下游，global 全部重来
最终      → Planner 汇总各步结果给出 final answer
```

它和 ReAct 最本质的结构差异：**Step 是带状态的显式对象**。代价与收益都在这里——收益是每步上下文恒定（不随全局进度膨胀），代价是要为"先想后做"付出三重税（第四节实测）。

它也是重规划实验（E2）的载体。一条真实的三连环局部重规划 trace（`main` 批次 `plan_execute_T1_easy_r1`）：

```text
[ 13.2s] initial:        1:PEND 2:PEND 3:PEND 4:PEND 5:PEND 6:PEND
[108.5s] replan:local#1: 1:DONE 2:DONE 7:PEND 8:PEND          （3-6 被替换）
[175.7s] replan:local#2: 1:DONE 2:DONE 9:PEND 10:PEND 11:PEND （7-8 被替换）
[234.5s] replan:local#3: 1:DONE 2:DONE 12:PEND 13:PEND 14:PEND（9-11 被替换）
[308.3s] final:          1:DONE 2:DONE 12:DONE 13:DONE 14:DONE → 成功
```

注意 DONE 的步骤 1、2 在三次重规划中都被保留——这正是局部重规划的意义，也是它的隐患（DONE 步骤的前提如果被新计划改变，不一致会残留；本实验刻意不修这一点，因为它就是 E2 要观测的现象）。

### 2.3 Reflexion：外环 + 言语记忆池

```text
for epoch in range(4):
    内环 = run_react(..., extra_context=memory.render())   # 记忆注入 system
    判定 = 评估器(strict / schema / llm_judge 三档)
    通过 → break
    memory.add(reflect(本轮轨迹摘要, 评估器反馈))            # ≤80 词、要具体可执行
```

记忆池只留最近 3 条教训。每轮反思只看**本轮**的轨迹（`_condense_trajectory` 从本轮首个事件开始摘要）——这是对原始草稿两处影响结论的 bug 的修正（评估器吃真实 effects、反思不吃全部历史）。

Reflexion 的设计前提是：**失败可复利**——每次失败产生具体的、可迁移的教训。这个前提需要两个条件同时成立：任务一次写对的概率低、且判定器给出的失败信号具体。T3（隐藏单测）就是按这个前提设计的。

### 2.4 CoT：null baseline

无工具、单次调用、明确告知 "You have NO tools"。它的唯一作用是标定"没有脚手架"的下限。

## 三、实验设计

### 3.1 任务按结构属性分型，不按"谁擅长"

三个任务由两个正交的结构属性选出（信息需求何时可知 × 有无硬判定器）：

| 任务 | 类型 | 信息需求 | 硬判定器 | 场景 | 主场 |
|---|---|---|---|---|---|
| T1 | 探索型 | 执行时才可知 | 测试套件 | 遗留仓库排障：报错指向 `billing.py`，真根因在 `hashes.py` 的过期 hash 常量 | ReAct |
| T2 | 规划型 | 一开始完全已知 | SQL 交叉校验 | 数仓算 2023 整体毛利率，埋 5 个坑 | Plan |
| T3 | 校验型 | 一开始已知 | **隐藏单测** | 按规格实现函数，提交后跑隐藏测试 | Reflexion |

**对角线是主场，非对角线才是信息量。** 如果范式的影响是真实的，客场应该显著输给东道主；如果全打平——那本身就是最有价值的结论。

三组陷阱各不相同：

- **T1**：两个（easy）/ 四个（hard）红鲱鱼文件（`api.log` 的 RETRY、`http_client.py` 的空超时、`storage.py` 的可疑 `_normalize()`、`metrics_collector.py` 的 WARN）；读错文件不会立刻报错——ReAct 的目标漂移在这里可观测；不允许改 `tests/`；不许破坏 `billing.py`（防"把断言改对"式作弊）。
- **T2**：① `sales` 有重复行（必须 DISTINCT，忘了答案从 0.55 变 0.7）；② `cost` 里有 `999.0` 的 legacy 毒行；③ 2018 年前不可查；④ `targets` 缺 south region（要用数据字典里的 `DEFAULT_TARGET=400`）；⑤ `fetch_warehouse_export` **永远 403**——逼你放弃"一次性导出"的捷径，老老实实用 SQL 逐步算。真值 0.55 由 ground-truth SQL 交叉校验得出，不写死常量。
- **T3**：隐藏单测是硬判定器，失败信息逐条指向具体边界用例（`"500MS"` 大小写、`"1h 30m"` 复合非法、空串 → `"-"`、bool 不 coerce……）；规格里埋了一处矛盾描述（legacy 行为段落 vs 主规格），模型必须自行取舍。9 条隐藏测试，参考实现全绿。

### 3.2 预注册假设（跑之前写死，避免事后拟合）

| # | 假设 | 结果（第五、六章逐条核对） |
|---|---|---|
| H1 | ReAct 在 T1 上不输 Plan | ✅ 成立（但真正的差异在成本） |
| H2 | Plan 在 T2 上峰值 prompt 比 ReAct **低一个数量级** | ❌ **推翻**（只有 1.3×；累计反而 2×） |
| H3 | Reflexion 在 T3 成功率最高、¥/成功最贵 | ❌ **推翻**（成功率持平且更便宜） |
| H4 | 局部重规划 ≈ 全局、成本更低 | ⏸ 未测（预算缩减，E2 未跑） |
| H5 | 强模型下三范式成功率趋同——范式是**成本压舱石**而非能力放大器 | ✅ **强烈成立（本文主结论）** |
| H6 | 偏心裁判下 Reflexion 成功率下降 | ⏸ 未测（E3 未跑；有一段定性证据） |

### 3.3 度量口径

- 成功率：k/n + Wilson 95% CI；本实验每格 N=3（react 与 plan/T1 为 N=9–10），是**趋势级**证据；
- 时延：模拟服务时钟（`450ms + fresh_prompt×0.02 + completion×12ms`，缓存命中 40ms），真实 wall-clock 另存不入主表；
- 成本：三档计价（cached 0.2 / fresh 2.0 / output 8.0 元每百万 token），按 API 报告的缓存命中分档；
- 评估器只信**记录的副作用**（effects），永远不信模型的自我汇报；
- 最终成绩一律 strict；`schema`/`llm_judge` 只在 Reflexion 内环演示弱判定器（E3）。

## 四、实测结果：成功率无差别，成本有断层

### 4.1 成功率矩阵

**easy**

| | T1 探索 | T2 规划 | T3 校验 |
|---|---|---|---|
| ReAct | **10/10** ✅主场 | 10/10 | 10/10 |
| Plan-Exec | 10/10 | **3/3** ✅主场 | 3/3 |
| Reflexion | 3/3 | 3/3 | **3/3** ✅主场 |
| CoT（无工具） | 0/3 | 0/3 | 3/3 |

**hard**

| | T1 探索 | T2 规划 | T3 校验 |
|---|---|---|---|
| ReAct | **10/10** ✅主场 | 10/10 | 9/9 |
| Plan-Exec | 6/6 | **3/3** ✅主场 | 3/3 |
| Reflexion | 3/3 | 3/3 | **3/3** ✅主场 |
| CoT（无工具） | 0/3 | 0/3 | 3/3 |

三个带脚手架的范式：**105/105，100%，主场客场零差别**。Wilson 区间在这个样本量下宽（3/3 对应 [0.44, 1.00]），所以严谨的表述是：**没有观察到任何范式在任何任务上的成功率劣势**——而预注册的 H2/H3 恰恰预言了相反方向的显著差异。

唯一失败的是 CoT，而它的失败模式高度结构化（第五节）。

### 4.2 结构指标：范式差异的真实居所

各范式全部运行的中位数：

| 范式 | 成本 | 峰值 prompt | 累计 prompt | 累计/峰值 | LLM 调用 | 首个动作时刻 | 模拟耗时 | 真实耗时 |
|---|---|---|---|---|---|---|---|---|
| ReAct | **¥0.031** | 3.9K | 16.8K | 4.3× | 7 | **1.0s** | 34.8s | 18.6s |
| Plan-Exec | ¥0.097 | 4.8K | **62.7K** | **13.0×** | 26 | 11.0s | 112.7s | 58.4s |
| Reflexion | ¥0.031 | 4.5K | 17.0K | 3.8× | 7 | 1.0s | 35.6s | 21.1s |
| CoT | ¥0.065 | **0.27K** | 0.27K | 1× | **1** | — | 96.6s | 59.7s |

四个观察，每个都配得上展开：

**① Plan 的三重税。**
- *首动作税*：Plan 首个可观测动作（plan 事件）中位数 **11.0s**，ReAct 是 **1.0s**——先想后做，想的过程就是第一个副作用之前的时间。对交互式场景，这是用户盯着屏幕的 10 秒。
- *重发税*：Plan 的累计/峰值比是 **13×**，全场最差。它的"每步上下文恒定"是真的（峰值 4.8K，和 ReAct 相当），但**每个步骤的每一轮都要重发**任务+上游结果+工具 schema——"干净"是按次数付费的。T2 上 Plan 累计 28K vs ReAct 14K：**声称上下文更干净的范式，累计 token 反而是 ReAct 的 2 倍**。H2 预言的"低一个数量级"在峰值上只有 1.3×（3110 vs 2480，easy），在累计上是负收益。
- *规划税*：T1（探索型）上 6/10 个 run 触发了重规划（第二节那条三连环 trace），单 run 最贵 **¥0.36、57 次 LLM 调用**——是 ReAct 同任务中位数（¥0.04）的 9 倍。探索型任务上"先规划"买不到成功率，只买到账单。

**② Reflexion 与 ReAct 无法区分——因为外环从未转起来。** 18/18 个 run 全部 epoch=1、reflections=0：内环 ReAct 拿着 `write_solution` 的测试反馈就地自纠，第一轮就过了，外环的言语记忆一次都没用上。这在 T3（Reflexion 的设计主场、硬判定器、一次写对概率低）上也成立。**当工具反馈本身就是硬判定器时，跨尝试的言语反思是死重。**（它至少没变贵——外环空转的代价约等于零。）

**③ CoT 的两副面孔。** T3 上 3/3 全过、¥0.018–0.10，和脚手架们打平——纯生成任务上，脚手架一分成功率都买不到。T1/T2 上 0/18——因为它**没有环境访问权**。这是本文最干净的对照组结论：**Agent 脚手架买到的东西，排序第一的是环境访问权（工具循环），不是推理能力。**

**④ 无状态重发税是全体的。** ReAct/T1 的峰值 6.2K、累计 42.8K（6.9×）——这就是"每轮重发全量"的账单。但要归因给 ReAct 的只有峰值那一栏；累计那一栏，Plan（13×）付得更多。

### 4.3 帕累托前沿

把每个 (范式, 任务, 难度) 格子画在「成功率 × 成本」平面上（成本为中位数，成功率带 Wilson CI）：

```text
成功 1.0 ┤ R ●         R ●         R ●        ← react：三任务全 1.0，¥0.011–0.048
         ┤   P ●         P ●         P ●      ← plan：同样 1.0，¥0.045–0.138（右移 3×）
         ┤     X ●         X ●         X ●    ← reflexion：1.0，¥0.010–0.052
         ┤
成功 ~0  ┤ C ●         C ●                   ← cot：T1/T2 归零，T3 却是 1.0（¥0.018–0.10）
         └──┬────────┬────────┬────────┬──→ 成本 CNY
           0.01     0.05      0.10     0.36   （单 run 最贵：plan/T1/easy ¥0.36）
```

前沿完全由 **react ≈ reflexion** 占据（两者统计上不可区分），plan 在同一成功率上右移 3 倍，cot 在 T3 上勉强摸到前沿、在 T1/T2 上跌出平面。**在"成功率已经饱和"的象限里，范式选择纯粹是成本/时延决策。**

## 五、失败模式分布：全部 12 个失败都在对照组

123 次正式运行里共 12 次失败，**全部来自 CoT**：

| 格子 | 失败模式 | 次数 |
|---|---|---|
| cot / T1 / easy, hard | `tests_never_run` | 6 |
| cot / T2 / easy, hard | `no_value_in_answer` | 5 |
| cot / T2 / easy | `no_sql_executed` | 1 |

CoT 在 T2 上的回答是**诚实的**（`m2-cot` 批次 `cot_T2_easy_r0`）：

> *"Cannot compute the 2023 overall gross margin because the SQLite database and data dictionary are not accessible in this environment; the required regional revenue, cost, annual targets, and DEFAULT_TARGET are unavailable."*

模型完全理解任务，也完全知道缺什么——缺的不是推理，是**手**。

另两个"零事件"同样有信息量：

- **护栏零触发**（0 次 guard）：全部 123 run 中没有出现同一工具调用连续重复 3 次。 folklore 里"ReAct 会原地打转"的行为，在这个模型强度上没有出现。
- **Reflexion 外环零触发**（18/18 epoch=1）：见 4.2②。

还有一个反例值得单独说：探针阶段有一个 Reflexion/T2 run 跑满了 **4 个 epoch、3 次反思、¥0.096**（同任务 ReAct 只要 ¥0.02）——起因是当时评估器的一个抽取 bug 把正确答案误判为错误。它歪打正着地演示了 Reflexion 的失效动力学：**当判定器持续说"你失败了"（无论对错），外环就会 faithfully 地把成本乘上 epoch 数**。这正是 E3（偏心裁判）要正面研究的机制——裁判往"宽容"方向偏时反思幻觉、往"苛刻"方向偏时成本爆炸，两个方向的病灶是同一个：**Reflexion 的生命线是判定器的质量，而不是反思本身**。

## 六、结论：范式是成本压舱石，不是能力放大器

### 6.1 假设核对总表

| # | 预注册假设 | 裁决 | 证据 |
|---|---|---|---|
| H1 | ReAct ≥ Plan（T1 探索） | ✅ 成立，但内涵迁移 | 成功率 10/10 vs 10/10；成本 ¥0.04 vs ¥0.138（3.3×）；6/10 run 重规划 |
| H2 | Plan 峰值 prompt 低一个数量级（T2） | ❌ 推翻 | 峰值 1.3×（3110 vs 2480）；累计反而 2×（14K vs 28K） |
| H3 | Reflexion 在 T3 最准最贵 | ❌ 双向推翻 | 成功率与 ReAct 持平；hard 档更便宜（¥0.034 vs ¥0.048）；反思 0 次触发 |
| H4 | 局部重规划优于全局 | ⏸ 未测 | E2 未跑（预算）；已观测到 3 连环局部重规划 trace |
| H5 | 强模型下范式趋同 | ✅ **主结论** | 105/105；差异全在成本/时延/结构 |
| H6 | 偏心裁判伤害 Reflexion | ⏸ 未测（有定性反证） | 误判评估器引发 4-epoch 成本爆炸（探针 run） |

### 6.2 那"各有主场"的说法错了吗？

没有错，但**过期了**。"ReAct 适合探索、Plan 适合结构化流程、Reflexion 适合可验证的试错"——这些论断在模型一次做对概率低的世界里是真的：那时范式决定你能不能把任务做完。2026 年的中等模型在本文的任务结构上已经把"能不能"抹平了，范式的战场整体后撤到"以什么代价做完"：

| 你在乎什么 | 选什么 | 实测依据 |
|---|---|---|
| 端到端便宜、动手快 | **ReAct** | ¥0.031 中位、首动作 1.0s |
| 过程可审计、步骤可并行、上下文按步隔离 | **Plan-and-Execute** | 为此付 3× 成本 + 11s 首动作税 |
| 判定器**不可靠或不可即时获得**（事后验收、人工评审、弱信号） | **Reflexion** | 唯一在"反馈缺席"时仍有跨尝试记忆的范式；判定器可靠时它退化为 ReAct（本次实测形态） |
| 任务纯生成、无环境交互 | **什么都不用加** | CoT 在 T3 上 3/3、成本相当 |

一个更尖锐的表述：**Reflexion 的外环是给"没有硬判定器的世界"准备的补偿机制**。一旦 `write_solution` 这类工具把硬判定器塞进了轨迹内部，补偿机制就自动下岗——本文 18/18 的 epoch=1 是这个判断的直接观测。反过来说，如果 your 判定器是"事后人工验收"，内环工具反馈不存在，Reflexion 的记忆池就是全场唯一能跨尝试复利的东西。**范式选择的第一性问题不是"任务长什么样"，而是"判定器在哪里、什么时候到"。**

### 6.3 混合架构的实测依据

原计划的第六章要给混合架构建议。实测数据支持的最小建议：

1. **默认 ReAct**，除非你有下面两条之一；
2. **流程需要人类可读的中间产物**（审计、并行、断点续跑）→ Plan-and-Execute，并把重规划 scope 设为 local、上限设 2 次（实测 3 连环重规划后 4.0 的边际收益趋零、成本线性涨）；
3. **判定器在轨迹之外**（事后验收）→ Reflexion 外环套 ReAct 内环；判定器质量不可控时，宁可提前熔断也不要让外环空转烧钱（4.2 的反例）；
4. 无论哪个，**把硬判定器做成工具塞进内环**——这是把 Reflexion 退化成 ReAct 的那一步，也是省钱的那一步。

### 6.4 局限性（诚实清单）

- **样本量**：每格 N=3（react、plan/T1 为 9–10），趋势级证据；Wilson 区间宽，"100%"应读作"未观察到失败"。
- **单一模型**：DeepSeek-V4.1-Flash。H5 的"强模型趋同"需要 E4（更强模型对照）才能定界——v4-pro 跑同样矩阵是本实验最直接的续作。
- **模拟时钟**：解码主导的时延模型（12ms/token）。真实服务端 KV 缓存命中率高时，ReAct 的实际账单会比本模型更友好；相对排序稳健，绝对值要打折读。
- **N 不齐**：预算中途从 10 降到 3（react 已有 10/格的数据直接复用），矩阵如实标注了每格 n。
- **T2 两档真值同值**（都是 0.55），hard 只加了噪声行/诱饵 region，难度梯度弱于 T1/T3。
- **E2/E3 未跑**：局部 vs 全局重规划、偏心裁判对照停留在设计 + 单 run 定性证据。
- **任务族少**：每个结构属性只有一族任务，结论应读作"该结构类型的案例研究"。
- **提示词是脚手架的一部分**：四个范式的提示词已尽量对齐（同样的任务文本、同样的错误分层说明），但任何提示词对比都无法完全排除措辞混淆。
